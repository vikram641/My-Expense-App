## Receipt Scanner feature (added 2026-08-24)

Tapping **"Scan Receipt"** on the Add Expense screen opens a custom in-app camera scanner, photographs the receipt, and sends the **image itself** to Gemini for full-field extraction — no local OCR, no regex heuristics. (An earlier iteration this same session did on-device ML Kit OCR + regex parsing + a text-only Gemini call for category only; that approach was replaced because sending the image directly to a multimodal model is far more accurate for every field, not just category — see git history / this file's own edit history if you need the old approach for reference.)

1. **Camera UI** — `feature/scanner/ReceiptScannerFragment.kt` + `fragment_receipt_scanner.xml`. CameraX (`Preview` + `ImageCapture`, back camera, `CAPTURE_MODE_MINIMIZE_LATENCY`). `ScannerOverlayView.kt` draws the dimmed background + rounded-rect cutout + corner brackets (offscreen-bitmap `PorterDuff.CLEAR` technique). A `View` animates top-to-bottom as the "scan line" via `ObjectAnimator`.
2. **Capture → Bitmap** — `ImageCapture.OnImageCapturedCallback.onCaptureSuccess` delivers an in-memory JPEG `ImageProxy`; `imageProxyToBitmap()` decodes `planes[0]`'s buffer via `BitmapFactory` and applies `imageInfo.rotationDegrees`. The photo is **never written to disk** — held in memory only for the Gemini call, then discarded (bitmap goes out of scope after `readReceipt()` returns; `image.close()` happens immediately after decode).
3. **Extraction — one multimodal call, all fields at once** — `feature/scanner/GeminiReceiptExtractor.kt`. Sends the `Bitmap` + a text prompt to **Gemini (`gemini-3.7-flash`) via Firebase AI Logic**, with a `Schema.obj(...)` response schema forcing structured JSON output: `amount` (integer), `date` (string, asked for `yyyy-MM-dd`), `merchant` (string), `category` (`Schema.enumeration` constrained to the caller's actual category names + `"NONE"` — guarantees the model can't return a category that doesn't exist in this user's list). All four fields are optional in the schema and independently nullable in `ExtractedReceipt` — a field is only set on the form if the model actually returned it. On any exception/timeout (15s), returns `null` and the scanner shows "Couldn't read receipt, try again" without touching the form.
4. **Category names passed in, not looked up by the scanner** — `AddExpenseFragment` passes its already-loaded category *names* (not full objects, no `Parcelable` needed) as a `String[]` `Bundle` arg (`ReceiptScannerFragment.ARG_CATEGORY_NAMES`) when navigating to the scanner. The scanner only ever deals in category **names** (for the Gemini schema); `AddExpenseFragment` resolves the returned name back to an id by matching against `lastLoadedCategories` before calling `catAdapter.preselect(id)`.
5. **Result passback** — individual extras (`amount`/`date`/`merchant`/`category` strings + a `Boolean` `KEY_HAS_RESULT` sentinel) via Navigation's `savedStateHandle` result API (`ReceiptScannerFragment` → `previousBackStackEntry`; `AddExpenseFragment` → `currentBackStackEntry`, consumed once via `handle.remove(...)`). The `KEY_HAS_RESULT` boolean is the field actually observed (rather than one of the nullable string keys) since every string field can legitimately be absent on a partial read.
6. Every autofilled field stays a normal, freely-editable `EditText`/`TextView`/category-adapter selection — nothing is ever locked based on scan results.

### Threading gotcha that caused a real crash (fixed 2026-08-24)

`ImageCapture.OnImageCapturedCallback` methods run on the executor passed to `takePicture(executor, callback)` — i.e. a **background thread pool**, not main. The first version of `onCaptureSuccess` called `readReceipt(bitmap)` directly, which synchronously called `setHint(...)` (a view mutation) before ever hopping threads → `android.view.ViewRootImpl$CalledFromWrongThreadException`, reliably crashing on every real capture. Fixed by wrapping the post-decode handoff in `requireActivity().runOnUiThread { ... }` inside `onCaptureSuccess`. `lifecycleScope.launch { }` further down is safe on its own (its default dispatcher is `Main.immediate`), but anything that touches views **before** that `launch` call must already be on main. If you touch `b.*` anywhere inside a CameraX callback, assume you're on the wrong thread until proven otherwise.

### Verified real-world result (2026-08-24)

Tested against an actual printed Domino's Pizza receipt (Total 471.90, date 8/8/2019): extraction returned amount `472` (correctly rounded to match the app's integer-only amount field), merchant `"Domino's Pizza"`, date `2019-08-08`, category `Food` — all four fields correct in one pass, no manual correction needed.

### Accuracy fix — crop to overlay frame before sending (2026-08-25)

Follow-up after real-world use showed the single-multimodal-call approach above was still inconsistently accurate. Root cause: the captured photo was the **full, uncropped camera frame** — the on-screen scan rectangle (`ScannerOverlayView`) was only ever a visual guide, never applied to what actually got sent to Gemini, so background/table clutter around the receipt competed with the receipt for the model's attention.

- `ReceiptScannerFragment.onCaptureClicked()` now reads `previewView`'s width/height and `scannerOverlay.frameBounds()` on the main thread (before `takePicture`, since the capture callback runs on a background executor), then `cropToFrame()` maps that view-space rect onto the full-resolution captured bitmap and crops to it (8% padding beyond the frame, since it's a guide not a hard boundary) before the bitmap ever reaches `GeminiReceiptExtractor`.
- The mapping accounts for `PreviewView`'s default `FILL_CENTER` scale type (the displayed preview is a center-crop of the camera stream) using only the view's and bitmap's aspect ratios — no dependency on actual camera stream pixel dimensions, since preview and capture share the same field of view when bound together without explicit differing target resolutions.
- Also tightened `GeminiReceiptExtractor`'s prompt: explicitly instructs picking the grand total/amount paid over a subtotal or tax line when multiple money lines are present, and how to resolve ambiguous day/month date ordering (previously just said "yyyy-MM-dd" with no guidance on *which* number is the total or how to interpret an ambiguous printed date).
- Not yet re-verified against a new physical receipt — the original Domino's test above predates this change. Re-test before assuming these two fixes alone resolved the accuracy complaint.

  - `GenerativeBackend` lives in `com.google.firebase.ai.type`, not `com.google.firebase.ai` (easy to get wrong).
  - `Firebase.ai(backend = GenerativeBackend.googleAI()).generativeModel("gemini-3.7-flash", generationConfig { ... })`, then `model.generateContent(content)` is a suspend fun returning `GenerateContentResponse`, read via `.text`.
  - Multimodal prompt: `content { image(bitmap); text("...") }` (top-level `content` DSL, `com.google.firebase.ai.type.content`) — `javap` shows these as `addImage`/`addText` on `Content.Builder`, but the real Kotlin call names are `image(...)`/`text(...)`.
  - Structured JSON output: `generationConfig { responseMimeType = "application/json"; responseSchema = Schema.obj(propsMap, optionalPropsList) }`. `Schema.obj(...)`/`.array(...)`/`.enumeration(...)`/`.boolean(...)` call names match `javap` directly, but `Schema.numInt()`/`Schema.str()` (javap names) are actually `Schema.integer()`/`Schema.string()` in Kotlin source. Use the shortest positional overload (e.g. `Schema.string()`, `Schema.enumeration(listOf(...))`) to sidestep guessing named-parameter names, which `javap` can't reveal at all.

## Onboarding replaces login on first run (added 2026-08-25)

The first-run experience is now a name/budget/currency onboarding flow instead of Login/Register — but **Login/Register were not deleted**, only bypassed (see "Offline mode" below for why). If a future session needs to re-enable login, everything is still there, just commented out at the call sites documented below.

1. **A separate Activity, not part of `MainActivity`'s nav graph** — `feature/onboarding/OnboardingActivity.kt` + `activity_onboarding.xml`, hosting its own `NavHostFragment`/`nav_graph_onboarding.xml` (`app:navGraph="@navigation/nav_graph_onboarding"`), registered in `AndroidManifest.xml` as a non-exported activity using `@style/Theme.Expense`. This was a deliberate ask (separate Activity, screens as Fragments within it) rather than folding onboarding into the existing `nav_graph.xml`.
2. **8 screens, all Fragments**, in navigation order:
   - `WelcomeFragment` (`fragment_onboarding_welcome.xml`) — hero + "Get Started".
   - `OnboardingFeatureFragment` **reused three times** (`featureScanFragment` → `featureAutoDebitFragment` → `featureAlertsFragment`) — one Fragment class, one layout (`fragment_onboarding_feature.xml`), with per-destination copy/icon/animation supplied as `<argument>` defaults in `nav_graph_onboarding.xml` (`icon_res`, `title`, `subtitle`, `step_index`, `button_text`, `animation` = `"scan"`/`"pulse"`/`"none"`, `next_action_id` — the last one is an `app:argType="reference"` pointing at that destination's own `<action>` id, so the shared Fragment can call `findNavController().navigate(nextActionId)` without knowing which screen it's on). Each has a "Skip" that jumps straight to `setupNameFragment` via `findNavController().navigate(R.id.setupNameFragment)` (a direct destination-id navigate, no declared action needed — NavController allows this for any destination in the current graph).
   - `SetupNameFragment` / `SetupBudgetFragment` / `SetupCurrencyFragment` — one Fragment each (structure differs enough per screen that a shared Fragment wasn't worth it), all writing into a shared `OnboardingViewModel` (`by activityViewModels()`) as the user moves forward, each with its own thin progress bar (`@drawable/progress_bar`, same drawable the Home budget card already uses) and a bordered back-circle button (`@drawable/bg_back_circle` + `ic_chevron_left`) that just pops the back stack.
   - `SetupCurrencyFragment` lists **all 14 currencies from the existing `CurrencyConstants.CURRENCIES`** (not a shortened list) via a plain `RecyclerView.Adapter` (`CurrencyAdapter.kt`) — added `CurrencyConstants.getSymbol(code)` (wraps `java.util.Currency.getInstance(code).symbol`) since nothing in the codebase resolved a currency code to its display symbol before.
   - `AllSetFragment` — recap card + "Start Tracking", the only screen that actually calls `OnboardingViewModel.completeOnboarding()` and `OnboardingActivity.finishOnboarding()`.
3. **Local-only persistence** — `core/util/OnboardingPrefs.kt`, a `@Singleton` SharedPreferences wrapper (`"prefs_onboarding"`) following the same pattern as `TokenManager`/`AvatarManager`/`SessionCacheManager` (every concern here gets its own tiny prefs class rather than a shared "app prefs" file). Stores `onboarding_complete` (the gate), `user_name`, `monthly_budget`, `currency_code`. The collected **budget is still not wired into the real per-category `BudgetEntity`/Room** — that's unstarted follow-up work. The collected **name now does show up everywhere the app displays it** (see point 6).
4. **Entry-flow rewiring — the actual bypass mechanism** — `SplashViewModel.verifyUserToken()` now checks `onboardingPrefs.isOnboardingComplete()` **first**: if incomplete, emits `NavEvent.ONBOARDING`; otherwise it goes straight to `NavEvent.HOME` unconditionally. The original JWT-token check (`if (!token.isNullOrEmpty()) HOME else LOGIN`) is commented out immediately below it, not deleted. `NavEvent` (`core/NavEvent.kt`) gained a new `ONBOARDING` case. `SplashFragment.observeState()` handles it by `startActivity(Intent(..., OnboardingActivity::class.java))` + `requireActivity().finish()`. `nav_graph.xml`'s `loginFragment`/`registerFragment` destinations and their actions are all still there, completely untouched — they're just unreachable from Splash now. `OnboardingActivity.finishOnboarding()` relaunches `MainActivity` with `FLAG_ACTIVITY_NEW_TASK or FLAG_ACTIVITY_CLEAR_TASK`, which re-runs Splash, which now sees `onboarding_complete = true` and goes straight to `dashboardFragment`.

6. **The onboarding name now shows up wherever the app displays a user name** (added later same day, after the first pass shipped without this): `HomeViewModel`, `SettingsFragment`, and `EditProfileFragment` all now inject `OnboardingPrefs` and seed their name/initials/currency display from it as the default, exactly the same "local data first, real server data overwrites it if a fetch ever succeeds" pattern as everything else in "Offline mode" below — none of the existing server-profile-fetch code paths were removed, just given a working fallback for when they fail (which, offline, is always). See `HomeViewModel.localGreeting()`/`initialsFrom()`, and the pre-fill lines near the top of `SettingsFragment.onViewCreated()` / `EditProfileFragment.onViewCreated()`.
7. **Layout bug fixed in all three Setup screens**: in each of `fragment_onboarding_setup_name.xml`, `fragment_onboarding_setup_budget.xml`, `fragment_onboarding_setup_currency.xml`, two sibling views were both constrained `app:layout_constraintTop_toBottomOf` the same anchor instead of chaining sequentially (e.g. the subtext line AND the field/amount-row/currency-list below it were both anchored to the headline), so they rendered on top of each other. Caught via on-device screenshots, not the emulator/build — this class of bug doesn't show up in a compile, only visually. Also fixed: the icon badge on those same three screens was constrained to the back button instead of the headline being constrained *below the icon* (same root cause, different pair of views) — check any new screen built this way for the same mistake before shipping it.

## Offline mode (temporary, added 2026-08-25)

The user's explicit plan: get the whole app working fully offline first, layer real server-sync back in later as a separate piece of work. Everything below was **commented out at the call site, not deleted**, specifically so it's easy to grep for and re-enable — search for "Offline mode (temporary)" to find every spot.

- **Server sync (`SyncWorker`)** — the only two call sites that still fired it are now disabled: `LoginFragment.kt` (`authViewModel.registerFcmToken()` and `SyncWorker.enqueueOneTime(..., LOGIN_SYNC)`, both commented right where the token gets saved) and `SettingsViewModel.logout()` (the `repository.syncData()` push-before-clearing-local-data step is commented; `logout()` now just does what `logoutWithoutSync()` already did — clear local data, call the logout API). `ExpenseApp.onCreate()`'s periodic/one-time `SyncWorker` enqueue calls were *already* commented out before this session (pre-existing, not new). `SyncWorker.kt` itself and `Repository.syncData()`/`getSyncForExpense()`/`getSyncForBudget()` were **left as-is** (not commented) since nothing calls them anymore anyway — touching working, self-contained code that's already unreachable seemed like unnecessary risk. If you bring sync back, `SyncWorker.enqueueOneTime(context, SyncWorker.LOGIN_SYNC)` after a successful login is the main re-entry point.
- **FCM token registration** — `AuthViewModel.registerFcmToken()`'s body is commented out (fetching a token from `FirebaseMessaging` and POSTing it via `repository.sendFcmToken()`); its only call site (`LoginFragment.kt`) is commented too. `MyFirebaseMessagingService.sendTokenToServer()` — called from `onNewToken()`, which Android still invokes normally — now just caches the token locally via `tokenManager.saveFcmToken(token)` and returns; the network POST (`repository.sendFcmToken(token)`) is commented out below it. **Incoming push notifications still work as before** (`onMessageReceived`/`showNotification` untouched) — only the "tell the backend which device this is" half is disabled, since nothing is meaningfully "logged in" to receive user-targeted pushes right now anyway.
- **Not touched**: `AuthInterceptor` (still attaches `Authorization: Bearer $token` to every Retrofit call — harmless no-op header when there's no token), `Repository`'s other still-authenticated API methods (expenses list, budgets, profile, etc. — whatever screens call them will just fail/show empty state offline, same as before this change), and the whole Login/Register UI (see "Onboarding" above). **Categories are the one exception** — that one crashed instead of failing quietly, so it got a real fix (Firestore instead of the authenticated endpoint) rather than just being left broken; see "Categories now come from Firestore" below.
- **Known gap**: nothing currently reads `OnboardingPrefs` outside of the onboarding flow itself — the Home screen's greeting and the real per-category `BudgetEntity` (Room) are unrelated to what onboarding collects, so a fresh install will finish onboarding and then likely see an empty/default Home and Budget screen rather than the name/budget/currency just entered. Wiring that up is explicitly *not done* — the user's plan treats this as a later step.

## Categories now come from Firestore, not the REST API (added 2026-08-25)

Real crash hit on-device after the offline-mode changes above: `Repository.getExpenseCat()` called the categories REST endpoint (`expenseApi.getExpenseCat()`), which needs a login token via `AuthInterceptor` - and since the app now runs without one (see "Offline mode" above), that call always 401s, and whatever screen loads categories first (Home tab, on a fresh install with an empty Room `categories` cache) crashed on the resulting error.

Fix: categories are default/global data, not user-specific, so they're served from a public Firestore collection instead of the authenticated REST endpoint - `Repository.getExpenseCat()` (`data/repository/Repository.kt`) now does `firestore.collection("categories").get().await()` and maps documents straight into the existing `CatDataResponse` → `CategoryEntity` → Room pipeline (`CategoryDao`, `CategoryMappers.kt`) completely unchanged - every consumer (`ExpenseCatAdapter`, `AddExpenseFragment`, `BudgetFragment`, etc.) needed zero changes, since they all already read from Room via that same pipeline. The old `utils.safeApiCall { expenseApi.getExpenseCat() }` line is commented directly above the replacement, not deleted. `FirebaseFirestore` is provided via a new `NetworkModule.provideFirestore()` (`Firebase.firestore`, no separate config - same `google-services.json` as the rest of the app's Firebase usage); `implementation("com.google.firebase:firebase-firestore")` added to `app/build.gradle.kts`.

**Firestore document shape**, collection `categories`, one doc per category (doc id = the category's `_id`): `{ id: string, name: string, color: string (hex), icon: string (matches a local drawable name, e.g. "ic_food"), isDefault: boolean }`. Seeded from `/Users/apple/Downloads/expense_tracker.categories.csv` (7 rows, exported from the old MongoDB `categories` collection) via a one-off admin script (`firebase-admin`, Python, using the service account key at `/Users/apple/Downloads/expenseapp-7b500-firebase-adminsdk-fbsvc-6eaa476f15.json`) - not part of the app or repo, just a manual upload.

**Resolved 2026-08-25, same day** - Firestore was not enabled on the project yet (`SERVICE_DISABLED`, and the service account lacked IAM permission to enable it itself), so the user created the database via Firebase Console → `expenseapp-7b500` → Build → Firestore Database → Create database (Native mode, `us-central1`) - a one-time manual step, same situation as the AI Logic setup earlier. After that: the upload script ran successfully (7 documents written), but a **second blocker** showed up - a freshly-created Firestore database defaults to fully locked security rules (`allow read, write: if false` on everything), so the app's unauthenticated read still got denied. Fixed by deploying custom rules (via the Firebase Rules REST API, using the same service account) that allow public `read` on just the `categories` collection and leave everything else locked: see the `match /categories/{categoryId} { allow read: if true; ... }` rule in the project's Firestore rules. Both the upload script and the rules-deploy script are one-off admin tooling, not part of the repo. Verified end-to-end on-device: Add Expense's category picker shows Food/Transport/Shopping/Health/etc. with their real icons and colors, no crash.

## Splash screen (redesigned 2026-08-26)

`fragment_splash.xml` used to show a plain white circle with a generic `ic_money` glyph on a flat `@color/accent` background, and the text "SpendSmart" (the old, never-finished rebrand's name). Replaced with: `bg_splash_gradient.xml` (a diagonal `progress_start → accent → progress_end` gradient - the same purple tokens used everywhere else, e.g. the onboarding screens and the home budget progress bar) as the background, `@mipmap/ic_launcher_round` (the actual app icon - it's already a polished wallet/coin/growth-bars mark, no need to hand-draw a second logo that would fight with it) at 132dp with a bit of elevation for a soft shadow, and the wordmark text changed to "FixMoney".

**Splash always shows, on every normal launch, first time included** (confirmed with the user rather than assumed - the alternative was skipping it entirely once onboarding is done). This fixed a real inconsistency: `SplashFragment.observeState()`'s `NavEvent.HOME`/`NavEvent.LOGIN` branches already had `delay(2000)` before navigating, but the `NavEvent.ONBOARDING` branch (added earlier when onboarding replaced login - see "Onboarding replaces login on first run") had no delay, so first-launch users skipped straight past the splash branding while every later launch showed it for 2s. Both branches now delay consistently.

**One deliberate exception**: right after onboarding finishes, `OnboardingActivity.finishOnboarding()` relaunches `MainActivity`, which re-runs Splash → Home - showing the branded splash a *second* time in the same sitting (once before onboarding, once immediately after), which read as a bug when the user hit it. `finishOnboarding()` passes an `EXTRA_SKIP_SPLASH_DELAY` intent extra (constant lives on `SplashFragment`, imported from there); `SplashFragment`'s `NavEvent.HOME` branch checks `requireActivity().intent` for it and skips just its `delay(2000)` on that one hand-off - the fragment still mounts for a frame or two before the coroutine navigates away (a brief, basically-unavoidable flash), but the 2s *hold* is gone.

**A "fix" for that residual flash was tried and reverted - real crash, not just a rejected idea, worth knowing about if someone's tempted to retry it**: swapping the `NavHostFragment`'s graph to start at `dashboardFragment` instead of `splashFragment2` in `MainActivity.onCreate()` (right after `setContentView`, before the first frame draws) so `SplashFragment` would never be created at all for this hand-off. This crashed every time: `IllegalArgumentException: Navigation action/destination action_splashFragment2_to_dashboardFragment cannot be found from the current destination Destination(dashboardFragment)`. Cause - the `NavHostFragment` had *already* created `SplashFragment` from the static XML graph (`app:navGraph="@navigation/nav_graph"` on the `FragmentContainerView`, resolved during `setContentView`'s inflate, before any of `onCreate()`'s own code after that line runs) by the time the graph-swap code executed; swapping the graph changed what the *current destination* was considered to be, but didn't stop the already-alive old `SplashFragment` instance's own coroutine from later firing `findNavController().navigate(R.id.action_splashFragment2_to_dashboardFragment)` - an action only valid from `splashFragment2`, which no longer matched the (now different) current destination. Two independently-navigating fragment instances racing against one NavController. Reverted in full (see the comment left in `MainActivity.kt` at the same spot) - **only** the `EXTRA_SKIP_SPLASH_DELAY`-in-`SplashFragment` fix described above is actually in place.

Every other route to `NavEvent.HOME` (a normal cold launch, not coming from onboarding) is untouched and still shows the full ~2s splash. If "skip splash after onboarding" should instead mean "skip it forever, on every subsequent launch" (a bigger change than what's implemented - this only skips the one immediate post-onboarding hand-off), that would need `OnboardingPrefs` consulted in `MainActivity`/`SplashViewModel` instead of a one-shot intent extra - and whatever approach is used, don't reach for changing the nav graph's start destination at runtime without solving the race above first.

**Status bar/nav bar color while splash is showing** - `MainActivity`'s root (`activity_main.xml`) has `fitsSystemWindows="true"` with its own background (`@color/bg_card`) painted behind the system bars, which is correct for the rest of the app but left a mismatched dark strip behind the status bar over this screen's purple gradient. `SplashFragment.onViewCreated()`/`onDestroyView()` now temporarily override `window.statusBarColor`/`navigationBarColor` to `@color/accent` (matching the gradient) with light system-bar icons while this fragment is visible, then restore transparent + the normal dark/light icon appearance (read from the same `"settings"`/`"dark_mode"` prefs `MainActivity` uses) once it's gone.

## Gotchas that bit this session (don't rediscover)

- **`AddExpenseFragment.kt`'s save path calls `inputValidation.apply { this.amount.toInt() }`** (as a validation side-effect, not stored) — meaning the app only ever supported whole-number amounts, no decimals. Anything generating an amount string (the receipt parser included) truncates to an integer to match this existing constraint. This is a pre-existing app limitation, not something introduced by the scanner feature.
- **Date format is `yyyy-MM-dd` everywhere** on this screen — `SelectDateDialog`'s callback (`AddExpenseFragment.kt`) writes it that way, and the edit-expense flow reads it straight from the backend in the same format. Any new code writing to `tvDate` must match this exactly.
- `ExpenseCatAdapter.preselect(categoryId: String)` already existed (used by the edit-expense flow) and was reused as-is for the scanner's category autofill — no adapter changes needed.
- The device's screen recording/adb tooling: `uiautomator dump` reliably fails with "could not get idle state" while the scanner screen's infinite scan-line `ObjectAnimator` is running — don't rely on it for locating buttons on that screen. Measuring button center from a `screencap` pixel-color search (or precomputing from the known dp layout + `wm density`) works fine instead.
- **`xmlns:tools` declared on one child `<TextView>` doesn't cover sibling elements using `tools:text` elsewhere in the same layout** — XML namespace scope only extends to an element's own descendants, not its siblings, so declaring it inline next to the first `tools:` usage instead of on the layout's root element reliably breaks `mergeDebugResources` with `AttributePrefixUnbound` on the *next* `tools:` usage down the file (hit this repeatedly while building the onboarding screens, once per file, before catching the pattern). Always declare `xmlns:tools="http://schemas.android.com/tools"` once on the root layout element.
